# Film Room audit — 2026-09-05

**Question asked:** does player tracking actually work, and can the app do the
majority of the heavy video editing on its own?

**Short answer:** yes on both, with the caveats below. Every suite in `tests/`
was run against freshly generated fixtures (41 suites, 855 checks, 0 real
failures). The default Follow press with the **real** vendored YOLOX model was
also driven end to end on the one body-shaped fixture — it ran the detection
path and held the player's feet to within 0.011 of the frame for the whole clip
— and that check is now part of `tests/lockon.js` so it stays true.

## How it was run

| | |
| --- | --- |
| App | `index.html` + `lockon.js` at `3790401` (main, v8 Sprint 5), served from `file://` |
| Browser | Playwright Chromium 141 headless (`/opt/pw-browsers/chromium-1194`) |
| Fixtures | all 17 regenerated with ffmpeg 7.0.2 (`pip install imageio-ffmpeg`) |
| Muxer proof | `FFMPEG=… node muxer.js` — real libx264 + AAC through `buildMp4()` |
| Not available here | H.264/AAC **encoders** in the browser (`VideoEncoder` is absent in this Chromium, so `fastexport.js`/`render.js` run their frame-count flow checks against the stubbed encoder, exactly as documented), and the real eval clips (`tests/realeval/clips/` is gitignored; footage never enters the repo) |

Real-footage tracking numbers therefore remain the ones recorded in `PLAN.md`
on 2026-08-25 (detection vs template, parent-verified ground truth: same-kit
53.2% vs 18.2% time-on-him, pan/leaves-frame 96.4% vs 19.4%, occlusion 52.5%
vs 21.4%, zero identity switches). Nothing in this audit contradicts them; the
harness that produced them (`realeval/selftest.js`, 44 checks) is green.

**What it does not do** (none of these are regressions — they are unbuilt or
deliberately declined, and they are the honest edge of "majority"):

- **Slow motion / speed ramps in exports.** Auto-Cut stores the fastest 1.5 s as
  `clip.ramp`, but no render applies it (decision log 2026-08-25: a ramp is a
  taste decision for the social cut, to be offered later). Playback speed in
  the app is study-only.
- Transitions between clips (cuts only), background music, colour/exposure
  correction, stabilisation, 16:9 zoom/crop in exports (pinch zoom is a view
  transform and is deliberately not exported), multi-camera, editing the
  source audio, archives over 4 GB (no ZIP64 — the writer refuses instead of
  writing garbage).
- The realtime (🔊) export in Chrome produces WebM, not mp4 — already listed
  under "Known refinements" in `PLAN.md`.

## Other findings from reading the code

1. **`APP_BUILD` is still `'v6.0'`** while v7 "Onyx" and five v8 sprints have
   shipped. Tracking reports, metadata exports and the eval baseline all stamp
   this value, so a report sent in from today's build says v6.0. Left alone
   here (bumping it is a release decision and the realeval baseline records
   the build); worth doing with the v8 close-out.
2. **Same-time seeks do not stall.** `seekVid()` carries a 2 s safety timeout
   and `exportRange()` has none, so it was worth measuring whether setting
   `currentTime` to its current value fires `seeked`. It does (0–1 ms in this
   Chromium), so a Follow press or export starting at the playhead does not
   pay the timeout. No change needed.
3. **Backward detection runs have no 25 s cap** (`trackLimitForDetect` goes to
   0), consistent with the forward path's "to the end of the clip" rule but
   unlike the template path. On a whole-game file "Where he came from" can run
   for minutes; Escape cancels and keeps what it found. Behaviour, not a bug —
   recorded so it is a choice rather than a surprise.
4. `sw.js`: when offline and the asset is not cached, the fetch handler
   resolves with `undefined` (network error either way). Cosmetic; the app
   itself is network-first with a cached fallback and all assets are
   pre-cached on install.
